# Graphics

PAL low-resolution 320×256, **four bitplanes** (sixteen colours), driven by a Copper list
that also does the colour work: gradients per raster line, the depth shades of the
starfield and the animated bar under the logo.

## Screen layout

| Rows (y) | Band | Content |
| --- | --- | --- |
| 0–7 | black | — |
| 8–71 | Logo | `UBER` (5× glyphs) over `CRACKING SERVICE` (2×), rules and corner brackets |
| 72–75 | Bar | animated colour bar (the `cop_raster_color` slot) |
| 76–195 | Middle | 3D starfield behind a rotating icosahedron wireframe + sprite ball ring |
| 200–215 | Scroller | 16-line scroller strip, with frame lines |
| 222–255 | Floor | animated Copper bars, no bitmap |

Display line = row + 44. The Copper wraps the vertical counter with `WAIT $FFDF,$FFFE`
for rows 212 and up (display lines above 255).

## Bitplanes and colour

The chip block holds four plane-sized buffers: plane 0, **wireframe buffer 0** (plane 1),
plane 2, **wireframe buffer 1** (plane 3). The display's plane 1 and plane 3 both show
the wireframe (double-buffered: `PatchCopper` alternates which physical buffer feeds
plane 1 and which feeds plane 3 each frame).

| Plane 0 | Plane 1 | Plane 2 | Plane 3 | Colour index | Used for |
| :-: | :-: | :-: | :-: | :-: | --- |
| 1 | | | | 1 | logo / scroller text (Copper gradient); mid-distance star |
| | 1 | | | 2 | wireframe (buffer A) |
| | | 1 | | 4 | far star (dim) |
| 1 | | 1 | | 5 | near star (bright) |
| | | | 1 | 8 | wireframe (buffer B) |
| any with p1/p3 | | | | 2, 8, 10, 12 | wireframe always in front of stars |

`COLOR01` and `COLOR09` are changed by the Copper per band, so the same plane-0 bit is
gold text in the logo, blue-white text in the scroller and a grey-blue star in the
middle.

## Wavy logo

Every logo row (8–71) has a `WAIT; MOVE COLOR00; MOVE COLOR01; MOVE BPLCON1` entry in
the Copper list (`cop_wave`, 16 bytes per row). `UpdateWave` rewrites the 64 `BPLCON1`
values each frame from the 256-entry `wave_tab`, indexed by `(4 · frame + 3 · row) &
255`: a sine of 2–14 pixels of horizontal scroll (the same nibble for both playfields),
about 1.3 waves over the logo and one wave per 64 frames. The tail below the logo
resets `BPLCON1` to 0.

Hardware scroll needs one extra word per line, so the display fetches 21 words
(`DDFSTRT` $30 instead of $38), the bitplane pointers point **2 bytes before** each
plane, and `BPL1MOD`/`BPL2MOD` are −2 (21 words fetched, 20 words per line). The extra
word at the left edge is hidden by the display window; with a scroll of *s* its last
*s* pixels slide in, which in the logo band are blank. The chip block carries a spare
longword before plane 0 for the first line's extra fetch.

## Logo

Generated by `tools/generate_assets.py` from a 5×7 glyph set: `UBER` at 5× scale and
`CRACKING SERVICE` at 2×, each centred on its ink, with two rules and corner brackets.
The validator requires every ink pixel to stay inside x = 1..318 and y = 1..62. The
white-to-orange gradient is pure Copper: one `COLOR01` change on every row.

## 3D starfield

64 stars, each with (x, y, z). Every frame `z` falls by 2; at z = 32 the star is sent
back to z = 255 with a new x and y from a 16-bit LCG. Projection is

```
screen x = 160 + x · 128 / z      screen y = 136 + y · 128 / z
```

so near stars race outward faster than far ones. A reciprocal table (`recip_star`)
replaces the division: `screen = (coordinate · recip[z]) >> 8`, one `MULS` instead of
`DIVS`. Stars outside the middle band are skipped.

Depth is shown as brightness using the planes the middle band leaves free: far
(z > 150) is plane 2 alone, mid (z > 80) plane 0 alone, near plane 0 + 2. Each star
remembers the byte offset, bit mask and class it was drawn with, and the next frame
erases exactly that — all stars are erased first, then all are drawn, so two stars
sharing a byte cannot erase each other.

Stars are single-buffered, which is safe because they are updated early in the frame
and finish before the beam reaches the starfield band.

## Wireframe: regular icosahedron

A **regular icosahedron** — 12 vertices, 30 edges, every vertex degree 5 — rotates in
a 120-line band. The vertices are the classical `(0, ±1, ±φ)`, `(±1, ±φ, 0)`,
`(±φ, 0, ±1)` set scaled to half-size 42 and rounded to the nearest integer:

```
  0: (  0,  26,  42)       4: ( 26,  42,   0)       8: ( 42,   0,  26)
  1: (  0,  26, -42)       5: ( 26, -42,   0)       9: ( 42,   0, -26)
  2: (  0, -26,  42)       6: (-26,  42,   0)      10: (-42,   0,  26)
  3: (  0, -26, -42)       7: (-26, -42,   0)      11: (-42,   0, -26)
```

24 edges have squared length 2696, 6 have 2704 (a 0.15 % spread — the closest regular
integer icosahedron at this scale). The validator checks: 12 vertices, 30 unique edge
pairs, every vertex degree 5, edge length spread ≤ 0.5 %.

The object also follows a motion path: the centre sways ±64 pixels and the distance
breathes ±18 units (`wire_cx`, `wire_zoff`), so the icosahedron swings from side to
side and in and out.

Per frame:

1. `DrawWire` selects the hidden buffer (opposite of `wire_front`).
2. The blitter clears the band (D-only blit, minterm 0) while the CPU works.
3. `CalcMatrix` builds one 3×3 rotation `Rz(k)·Ry(2k)·Rx(k)` from 7-bit sine/cosine
   tables, scaled by 128 (single `ang` counter).
4. `TransformVerts` rotates and perspective-projects the 12 vertices. Because every
   coordinate is 0 or ±42, the rotation is a sum of ±columns of the pre-computed
   `mat · 42` products — no per-vertex multiplication. Perspective:
   `screen = centre + r · 220 / (z + 300)` via a reciprocal table.
5. `BlitLine` draws each of the 30 edges with the blitter in **line mode**. The
   registers that never change between lines (A/B data, masks, C/D modulo) are set
   once per frame before the edge loop.
6. Next frame `WireSwap` points the Copper at the finished buffer, so the display
   never shows a half-drawn picture.

**Line mode.** The octant bits in `BLTCON1` come from the Hardware Reference Manual's
table 6-3 (`octants` in the source), `dmaj`/`dmin` are the larger/smaller of |dx|,
|dy|, and:

```
BLTAPT = 4·dmin − 2·dmaj    BLTAMOD = 4·(dmin − dmaj)    BLTBMOD = 4·dmin
BLTSIZE = ((dmaj + 1) << 6) | 2    BLTCON0 = (x1 & 15) << 12 | $0BCA
```

`ONEDOT` is left **clear**: it is for area-fill edges, and with it set shallow lines
come out with gaps. There is no clipping: the object is sized to stay inside its
band, and the emulation test asserts it.

## Copper-bar floor

The 34 floor rows (222–255) are one `WAIT; MOVE COLOR00` entry each (`cop_bars`, 8
bytes per row). Each frame `UpdateBars` resets them to a purple ramp (`floor_base`)
and then paints four bars of eight rows (magenta, cyan, gold, green; `bar_colors`,
bright core and soft edges) over them. Each bar's centre follows
`17 + 13 · sin(frame · (k + 2) + 64 · k)`, so the bars move at different speeds and
later bars are in front. All of these rows are below display line 255, after the
Copper's vertical-counter wrap.

## Scroller

Planar pixels are MSB first, so scrolling left shifts each row as big-endian
longwords from the rightmost to the leftmost with `ROXL`: bit 31 of one longword
falls into X and enters the next longword to its left at bit 0. X must start at zero
for each row, and `MOVEQ` does not touch it, so it is cleared explicitly with
`andi #$EF,ccr`. Every second frame the band moves one pixel, then the next column
of the current glyph is written into bit 0 of the last byte of each of the 16 rows
(each of the 8 font rows on two lines). The strip is far down the screen and is
shifted before the beam gets there, so it is single-buffered.

## Sprite ball ring

Eight hardware sprites (channels 0–7) orbit the wireframe on a tilted, spinning,
wobbling 3D ring. Each ball is drawn at one of three sizes (far/mid/near) with
corresponding brightness. `BPLCON2` bit 2 ($0002) puts sprites 4–7 (the far balls)
behind the playfield, so they pass behind the wireframe. The sprite pages are
pre-built in the chip block (`sprites`, 8 × 80 bytes); `UpdateSprites` patches the
sprite position and size words each frame.

## Copper

The list (in `chipdata.s`) sets display fetch/window registers, `BPLCON0` (four
planes), the six pointer pairs (`PatchCopper` rewrites the **data** words at offsets
2/6, 10/14 and 18/22 from `cop_bpl1` every frame, because planes 1 and 3
alternate), the static palette, and then the per-row entries: 64 wave rows, a
mid-band glow, the scroller strip and 34 bar rows. The wave and bar values are
patched at run time.

## Verification

`tools/emu_test.py` renders the Copper list and bitplanes exactly as the chipset
would show them and compares them with independent Python reference models: the logo
bitmap, every star position and depth class, every scroller pixel, the wave and bar
rows, and — on **every** frame — the whole displayed wireframe buffer against the
reference icosahedron projection and a reference Bresenham. The blitter's line mode
itself was confirmed on real (emulated) hardware by running the program in FS-UAE.
